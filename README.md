# Astra Data Factory

An Artizent platform where agents generate, test and operate data pipelines, migrations and data quality, and people approve. Give it a source description, a target profile and a domain pack; it produces running, tested, governed pipelines with the evidence behind them.

Product specification: [docs/product-spec-v0.2.md](docs/product-spec-v0.2.md). Backlog: [docs/backlog-v0.2.md](docs/backlog-v0.2.md). Decisions: [docs/adr](docs/adr). UX research: [docs/ux](docs/ux).

## Repository layout

| Path | Plane | Contents |
|---|---|---|
| `core` | shared | `astra-core`: line-aware YAML, problem reporting, schema error wording, Snowflake connection. Every plane depends on it. |
| `specs` | Knowledge (E2) | The spec registry: one directory per layout, one file per version, validated on every pull request |
| `knowledge` | Knowledge (E2) | `astra-spec`: the registry, resolution of the version in force, and later patterns, domain packs and the rule catalog |
| `domains` | Knowledge (E2) | Domain packs: glossary, canonical data model versions with rendered DDL and key tests, the rejection taxonomy and the reference-data feeds |
| `rules` | Knowledge (E2) | The rule catalog: one file per business rule with citation, class, owner, status and its history; configs reference rules by id |
| `configs` | Knowledge (E2) | Source configs, one YAML file per source, validated against the schema, the spec registry and the rule catalog on every pull request |
| `assessments` | Discovery (WBS 1.4) | Assessment memos with their evidence: the Normalizer decision's Spark transformers, their Snowpark Connect versions, recorded changes, samples, expected rows and harness results |
| `golden` | Verification (E4) | Golden datasets: per pilot custodian, how the legacy path is replayed, the index of every captured version (hash, source files, store reference), and how a captured output compares with the lakehouse (keys, fields, tolerances); the data lives in the golden bucket, read-only |
| `migrations` | Generation (E3) | Historical migrations driven through SnowConvert AI: one file per SQL Server source naming the schemas, the archive-store schema and the command line of each phase; results and logs land with the release |
| `releases` | Generation (E3) | Release bundles rendered from configs and domain packs (reference-data replication, Gold read models and the watermark) and written by migration runs (converted archive-store DDL with logs and results); deployed by the pipeline |
| `generation` | Generation (E3) | `astra-data`: config validation, bundle deploy and generated tests. The compiler and renderers grow here. |
| `verification` | Verification (E4) | `astra-verify`: ephemeral sandboxes per task, dry runs of a drafted config, golden dataset capture, replay of a config change against captured history, the parity engine and its report across a dual-run cycle window, the DQ runner and its per-entity scores, a connection sheet for the client's own DQ tool, the 3x volume test, chaos scenarios proving recoverability, a DR drill proving RTO and RPO, the agent evaluation harness (loading and scoring a gold set, plus, as of S6.3.6, `append_case` — the one function that writes one, a human's own accept/reject decision on an agent's draft turned into a new case, refused outright for a duplicate id or an unthresholded tier), and the Snowpark Connect assessment harness. |
| `agents` | Agents (E5) | `astra-agents`: bounded agent workers. The Spec Reader (S5.1.1) turns a layout document into a Source Spec draft, with page citations, a person's approval away from the registry. The Profiler (S5.2.1) reads a sample file against a spec already in the registry and flags a field whose observed data disagrees with the type the spec declares — read-only, samples only. The Pattern Matcher (S5.3.1) assigns an unclassified spec a family, tier and pattern list by comparing detail-record field shapes, and routes a genuinely new shape to the architect queue instead of guessing. Rule Recovery (S5.4.1) turns legacy Splitter/Loader Java into rule catalog entries with file:line citations, always `recovered`, never `confirmed` by the agent; T-SQL found is routed to SnowConvert AI, not parsed. The Modeler (S5.5.1) maps a spec to the domain pack's canonical model — a mapping can only target a real CDM column, a breaking model change is raised as a request and never applied, and a rule needing SME confirmation is tagged `CONFIRM_WITH_LOADER`. The DQ Generator (S5.6.1) proposes control-total, sign-field, date, key and pairing DQ rules straight from a spec's own structure — deterministic, no fabricated thresholds. The Test Generator (S5.7.1) turns a config's own `dq_rules` into SQL assertion tests and synthetic edge files, one branch at a time, entirely from its own fixed synthetic vocabulary. Exception Triage (S5.8.1) suggests a resolution per exception from the domain pack's own rejection taxonomy, grouped by root cause, with confidence from a measured acceptance rate; auto-apply needs both the taxonomy's whitelist and a track record that has earned it. The Drift Watcher (S5.9.1) compares a delivered file against its spec and proposes a delta — a record-length or code-set change — never writing to the spec itself. The Parity / Break Explainer (S5.10.1) explains every dual-run difference by rule, field and cause, reusing the real parity engine and compiled config rather than a second comparison. The Gate Evidence Compiler (S5.11.1) assembles a release's gate pack from seven named criteria (DQ, parity, volume, chaos, DR, agent evaluation, approval), each read from a tool's own already-computed pass/fail field; a criterion given no evidence is always listed and always shown NOT MET, never silently dropped. The Docs & Runbook Writer (S5.12.1) renders one doc per source straight into `docs/runbooks/sources/`, not a draft — the config, its spec, its domain pack's rejection taxonomy and its rule catalog are already approved, so it only presents them, the same way `astra-spec cdm render` already renders the canonical model; CI's `docs-writer render --check` fails a pull request that lets a doc go stale. Guardrails and autonomy (S5.13.1) closes out the Agents plane (E5): the L0–L3 autonomy level of every (agent, task class) pair as an append-only, approval-logged change history — a change needs an approver and a reason, and a change to L3 additionally needs a measured acceptance rate above a threshold over a stated window, or it is refused outright and never written; Exception Triage's own auto-apply now optionally consults it (`run --guardrails`) on top of its per-code confidence, never instead of it. Per draft agent, a gold set (`eval.yaml`) of reviewed inputs and correct output, scored by `astra-verify agent-eval` (S4.3.4); `agents/examples` holds worked examples for the Spec Reader, Profiler, Rule Recovery, Modeler, Exception Triage, the Drift Watcher, the Break Explainer and the Gate Evidence Compiler (all but Spec Reader's illustrative — no real sample file, legacy Java, live model run, exception data, captured dual-run or live Snowflake sandbox backs them yet), while `agents/pattern_matcher`, `agents/test_generator` and `agents/break_explainer` are real gold sets, built from the real `specs/` registry and the real `configs/examples/pershing_position.yaml` (plus, for the last one, the real `golden/pershing/parity.yaml`); the Docs & Runbook Writer and Guardrails have no gold set, having no draft to score. |
| `infra/terraform/foundation` | Control (E1) | Per environment: Snowflake database, schemas, roles, tier-sized warehouses, Iceberg bucket and external volume, Open Catalog sync, landing zone with Snowpipe and file load log |
| `infra/terraform/bootstrap` | Control (E1) | Once per AWS account: the bucket that holds Terraform state for every environment |
| `tools/opencatalog` | Control (E1) | Provisions and verifies Snowflake Open Catalog, which has no Terraform provider |
| `control` | Control (E6) | `astra-control`: the control plane application. The factory board (S6.1.1, ADR 0054) shows every custodian at its station (`profile`, `draft`, `dry_run`, `dual_run`, `cutover`), one WIP limit enforced per stream (blocking only what would newly put a stream over it, never a lateral move already in flight), custodians live per week. Config studio (S6.1.2, ADR 0055) drives a custodian through a guided `profile -> draft -> dry_run` sequence — every step recorded with who and when, on the board's own history, not a second log — and a promotion request: self-service for a simple-tier custodian, no engineer involved; anything else needs a distinct reviewer or the request is refused outright. Diff review (S6.1.3, ADR 0056) reuses `astra-verify`'s own `replay.config_diff` and the rule catalog's own `lineage` directly rather than computing either again — changed fields, every rule a diff touches with its real citation, and every other custodian that rule also affects; a citation becomes a real, openable reference (`specs/<id>/<version>.yaml#page=N`, or `<file>:<line>` for a legacy code citation), not just prose. Sign-in, roles and permissions (S6.3.1, ADR 0057) closes F6.3's first story: six closed roles (steward, BSA, engineer, ops, PM, auditor), each one's allowed actions listed and enforced at the CLI boundary via an optional `--role` on every command — omitted, a command behaves exactly as before; auditor reads everything and writes nothing, proven exhaustively against every write action. An identity provider's already-authenticated claims resolve to a role through a platform administrator's own group mapping; the live SSO redirect and token validation themselves need a real identity provider no environment here has. Home / my queue (S6.3.2, ADR 0058) aggregates approvals, exceptions assigned, breaks to explain and drift changes straight from the `report.json`/`gate_pack.json` files Exception Triage, Break Explainer, Drift Watcher and the Gate Evidence Compiler already wrote — no new agent import, no re-scoring — filtered by the same six roles; a gate pack only queues an approval once every other criterion is already met. The custodian page (S6.3.3, ADR 0059) puts family, tier, config version (effective date plus a real content hash), current station, files today against the cutoff, parity trend, open exceptions and cost in one place — every field read from something this plane already built (the board, a real parity report, `queue`'s own exception count) and shown honestly as "no data" wherever its own source, like a live file-load log or a cost figure with no FinOps agent to compute it, does not exist yet. The spec registry viewer (S6.3.4, ADR 0060) lists every field of a spec version with its real citation turned into an openable reference, and compares two versions by matching fields on `(record, name)` to highlight added, removed and shifted fields — checked against genuine drift already committed between `specs/pershing_gcus`'s own two versions (a new `lot_id` field pushing `filler` from position 67 to 79), not a staged example. The rule catalog browser and review (S6.3.5, ADR 0061) puts a rule's text, class and citation side by side, filtered by status, custodian or a `rejection-<code>` tag (the only place a rejection code lives in a rule today — no committed rule carries one yet), and confirms, rejects or marks a legacy defect by calling `astra-spec rules set-status`'s own already-real mutation directly rather than a second one — who, when and the comment are that function's own history entry, not new record-keeping; bulk confirm reaches every rule sharing the exact same text, this module's own definition of "identical," attempting each independently so one rule's own refusal never silently drops the rest. Steward's first write actions in this plane. Agent suggestion review (S6.3.6, ADR 0062) puts a Rule Recovery draft's own text and citation side by side, an edit diffed against the kept original, and accept/reject each appending a new case straight into that agent's own gold set (`astra_verification.agent_eval`'s own new `append_case`, refused outright for a duplicate case id or an unthresholded tier, never inventing one) — `expected` names which rule id should be recovered from the reviewed input, not its wording, so an edited draft's text changes what a reviewer compares but never what gets scored; steward and BSA share both write actions, the first action in this plane granted to two roles at once. No live Postgres yet: `board.yaml` and the promotion-requests log are real, working stand-ins for the store this plane will eventually use, the same relationship `astra-agents`' own approval and decision logs already have to a database. |

## Working in this repository

- Git is the system of record. Every generated artifact and every approval lands here; the factory database never holds the only copy of anything.
- Nothing secret is committed. Secret values live in the client's secret manager and are read by the pipeline at run time; a secret scan runs on every pull request and fails the build if one slips in.
- PII columns are tagged, masked for non-privileged roles, and their reads are recorded. See [ADR 0008](docs/adr/0008-secrets-access-history-masking.md).
- `make check` at the root runs everything CI runs on a pull request, without accounts. Each component has its own `make check` too.
- A merge to main deploys to dev; qa follows once a reviewer approves. See [docs/runbooks/ci-cd-setup.md](docs/runbooks/ci-cd-setup.md).
