# ADR 0048: Exception Triage suggests the taxonomy's own resolution and auto-applies only what a whitelist and a track record both allow

Date: 2026-09-13
Status: Accepted
Story: S5.8.1 Exception Triage: build and evaluate (E5, F5.8, WBS 2.5.15-2.5.17)

## Context

An exception is a row of the custodial domain pack's own CDM `Exception` entity (`domains/custodial/cdm/1.0.yaml`) — a rejection code, the value that failed, where it happened, and a status waiting for triage. Every one of the pieces this story asks for — a suggested resolution, whether a class may self-heal, what "L3, with audit" means — already has a home in `domains/custodial/rejections.yaml`, not a new format this agent invents: `RejectionCode.resolution` is the reviewed text a steward already wrote for the code, and `RejectionCode.auto_resolve`'s own schema description names this agent directly: *"Exception Triage may apply the resolution without a person (autonomy level L3, with audit)."*

## Decision

1. **A suggestion's text is the taxonomy's own `resolution` field, never invented.** No new suggestion vocabulary was written for this story; `Suggestion.resolution` is `RejectionCode.resolution` read straight from `rejections.yaml`, the same way DQ Generator's `check` text and Rule Recovery's rule `text` are read from something already real rather than generated fresh. A code with no taxonomy entry gets no suggestion — `unresolved_codes` names it — rather than a guessed remediation.

2. **The three named codes in this story are shorthand for the taxonomy's own names, not new codes.** `NEW_SECURITY` and `MISSING_TX_CODE` do not exist verbatim in `rejections.yaml`; the codes that mean what the backlog describes are `SECURITY_NOT_FOUND` and `TRANSACTION_CODE_UNMAPPED` (`ACCOUNT_NOT_FOUND` exists exactly as named). Renaming a real, already-committed taxonomy file to match a backlog story's own shorthand would be a breaking change to something every rendered pipeline already depends on, for no functional gain; this agent's own tests and example fixture use the taxonomy's real names and document the mapping here instead.

3. **Root cause is a mechanical grouping, not a claim about causation.** `_group_key` groups exceptions sharing a code and the same `raw_value` when there is one (the strongest signal — the same missing account number, the same unmapped transaction code, is obviously one underlying gap), falling back to the same `field_name`, and finally to the code alone. This is the closest a grouping can get to "the same underlying cause" without asserting *why* something failed, which this agent does not know and does not guess at.

4. **Confidence is a measured acceptance rate, Laplace-smoothed, not a model's opinion.** `acceptance_rate` is `(accepted + 1) / (total + 2)` over a plain, append-only decisions log (`record_decision`, mirroring `astra_knowledge.rules`'s own history-file shape) — a code with no recorded decisions yet starts at a neutral 0.5, and each real accepted or rejected decision moves it. There is no model call anywhere in this agent: the three named codes each have a single, mechanical, already-reviewed resolution, and grouping and confidence are both arithmetic over structured fields, the same reasoning that kept Profiler, Pattern Matcher and DQ Generator free of one.

5. **Auto-apply requires the whitelist and an earned confidence at once — the whitelist alone is not enough.** `auto_apply = whitelisted AND confidence >= AUTO_APPLY_CONFIDENCE` (0.8, a round starting number, not a pilot-measured one — the same honesty ADR 0043's tier thresholds and DQ Generator's severity default already used). This is not this agent inventing a stricter rule than asked: the product spec's own text says "Promotion to L3 requires a measured acceptance rate above a threshold over a stated window" (Section 8), and the CDM's `Exception.STATUS` enum already anticipates the result — `AUTO_RESOLVED`, *"resolved by a whitelisted rule, with audit."* The real, already-committed taxonomy currently whitelists two codes (`PRICE_MISSING`, `PRICE_STALE`, both `auto_resolve: true`); this story's own example fixture gives one a strong track record and the other a weak one, so only the first crosses the gate — proving the AND, not just the flag, decides.

6. **No L0-L3 admin system is built here.** Setting an agent's or a task class's autonomy level, and managing the self-healing whitelist as a product surface, is its own later story (`S6.3.12`, "Admin: autonomy levels and whitelist" — the backlog's own words: *"L3 cannot be set unless the measured acceptance rate is shown above threshold"*, which is exactly what `AUTO_APPLY_CONFIDENCE` already checks here, ahead of that admin surface existing). This agent only ever proposes and reports; whether its `auto_apply` suggestions are actually *applied* anywhere is a pipeline decision this story does not make.

7. **No real exception data exists anywhere in this repository** — an exception row is only ever produced at pipeline runtime (`generation/src/astra_data/render/resolve.py`, `merge.py`), the same situation Rule Recovery's illustrative Java and Test Generator's synthetic files were in. `agents/examples/exception_triage/exceptions.csv` (twelve rows, the CDM `Exception` entity's own columns) and `decisions.yaml` (a fabricated but internally consistent track record) are committed, clearly labeled illustrative fixtures — not a claim about real ops history.

## Consequences

- No eval gold set: like DQ Generator and Rule Recovery, this story's acceptance criteria are behavioral (a suggestion for three named codes, acceptance rate tracked, auto-apply gated correctly), not a precision/recall percentage against a reviewed answer — `test_the_story_acceptance_criteria_are_satisfied` proves all three directly against the real taxonomy and the illustrative fixture.
- `AUTO_APPLY_CONFIDENCE = 0.8` and the Laplace prior (`1`/`2`, a neutral 0.5 starting point) are both first-pass numbers; once real ops decisions accumulate, `S6.3.12`'s own admin surface is where a person would tune them, not a code change here.
- Adding `auto_resolve: true` to a new code in the real taxonomy is a steward's decision, not this agent's — this agent only reads the flag, and a code freshly whitelisted still starts at 0.5 confidence and needs a real track record before it auto-applies, by construction.
