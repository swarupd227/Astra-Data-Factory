# ADR 0052: The Docs & Runbook Writer renders into docs/, not work/ — there is nothing here to approve

Date: 2026-09-13
Status: Accepted
Story: S5.12.1 Docs & Runbook Writer: build and evaluate (E5, F5.12, WBS 2.5.23)

## Context

Every other agent in this plane writes a draft under `work/<agent>/...` for a person to review before it lands in `specs/`, `rules/`, `domains/` or `configs/` — the platform's own "agents propose, humans approve" rule (ADR 0044 and every agent ADR since). This story is different in kind: "source documentation and runbooks generated from artifacts" has nothing to propose. A compiled config, its spec, its domain pack's rejection taxonomy and its rule catalog entries are already registry data — already reviewed, already approved, already in Git. A doc rendered from them asserts nothing that was not already true before this agent ran; it only presents it, legibly, in one place.

That shape already exists in this repository. `astra_knowledge.cdm.write_rendered`/`check_rendered` render the canonical model's own DDL and key tests straight from the model, and `.github/workflows/ci.yml` already runs three checks of exactly this kind on every pull request: `astra-spec cdm render --check`, `astra-data reference render --check`, `astra-data gold render --check`. None of the three lands in `work/` for a person to accept; each fails the build when the checked-in file no longer matches what the source would render, and a person fixes it by running the render and committing the result. This story's two acceptance criteria point at the same shape: "runbook used successfully in the chaos drill" needs a stable, checked-in file a person reads while running `docs/runbooks/chaos-drill.md`, not a draft under `work/` nobody has approved yet; "docs regenerate on every release" is the render-and-check contract by name.

## Decision

1. **`astra_agents.docs_writer` writes into `docs/runbooks/sources/<bundle name>.md`, not `work/docs-writer/`.** `write_rendered`/`check_rendered` are the same shape as `astra_knowledge.cdm`'s: render every doc a set of compiled configs produces, remove ones no longer produced, and — for `check_rendered` — report every file that is missing, stale, or orphaned as a `Problem`, exactly the type `cdm.check_rendered` already returns. `<bundle name>` reuses `astra_data.render.names.bundle_name` unchanged — the same name the config's own release bundle already carries under `releases/`, so the doc and the release it documents are found by the same name.

2. **The doc answers two questions, both from data this agent does not invent.** *What does the chaos drill mean for this source?* `chaos_scenarios_for` walks the drill's own four fixed scenarios (`astra_verification.chaos.SCENARIOS` — duplicated here as a plain tuple rather than importing chaos.py's sandbox machinery for one constant; a test pins the two tuples equal) and, for `malformed` and `duplicate`, reads the exact taxonomy codes `chaos.py`'s own `_run_scenario` uses (`RECORD_TYPE_UNKNOWN`, `MERGE_DUPLICATE_KEY`) straight from `config.pack.rejections.code(...)` — the same `RejectionCode.description`/`.resolution`/`.severity` text the drill's own alert body is built from (chaos.py:320,325). `late` has no taxonomy code of its own (a timing fault, not a content fault, per ADR 0038) and is described as such. `truncated` ties to whichever `control_total` dq_rule this source's own config declares — read directly off `CompiledDqRule.check`/`.id`/`.severity` — and when a source has none, the doc says exactly that (`"no control_total dq_rule is configured"`) instead of fabricating a scenario the drill could not actually run for this source (ADR 0038 itself requires one). *What does this source raise, and what should a person do?* `resolution_rejection_codes` scopes the taxonomy to the entities this source's own `resolution` block actually resolves (`Account`/`Security`/`Transaction`/`Price`, read off `CompiledConfig.resolution`) — not every code in the taxonomy, which would bury a steward in codes this source cannot raise.

3. **Delivery and alerting are read from the config's own `delivery`/`alerts` blocks against ADR 0007's fixed rules, never invented.** "Late means the cutoff has passed... and at least one expected file pattern has no arrival" is ADR 0007 point 7's own wording, not a guess; a config with no `delivery` block (ADR 0007's consequence: "never goes late") is documented as such rather than showing a blank cutoff.

4. **No LLM.** Every fact in the doc already exists as a typed field on `CompiledConfig`, a `RejectionCode`, a `CompiledDqRule` or a `Rule` — the same "deterministic, no fabricated thresholds" shape as DQ Generator, Drift Watcher, Break Explainer and the Gate Evidence Compiler. There is no free-text generation task left over once the structured data is templated.

5. **Exit codes follow `cdm render`, not the other eleven agents.** Every other command's exit 1 means "the run found something a person should look at" — a draft. `docs-writer render` has no draft state: plain `render` exits 0 once it has written the current docs (there is nothing to review, only to keep); `render --check` exits 1 only when a doc is missing, stale or orphaned, exactly `astra-spec cdm render --check`'s contract. `cli.py`'s own module docstring documents this as a deliberate difference, not an oversight.

## Consequences

- CI's `agents` job gains one step, `astra-agents docs-writer render ../configs --check` (run from `agents/`, mirroring the `configs` job's own three `--check` steps) — a fourth render-and-check pair alongside the CDM model's, the reference-data bundles' and the Gold bundles'. A pull request that changes a config, a spec, the rejection taxonomy or a cited rule without re-running `docs-writer render` fails here, the same way a changed model fails `cdm render --check`.
- `docs/runbooks/sources/` is new and, today, holds one file (`pershing-position.md`, from the one real example config this repository has); every real config added later gets a doc the same way, with no code change to this agent.
- This agent's own committed `docs/runbooks/docs-writer.md` documents itself and the other eleven agents, not a source — those are still hand-written, matching how `agents/README.md`'s own per-agent sections are hand-written. Only per-source docs are generated.
