# ADR 0047: The Test Generator only synthesizes a branch it can prove correct at the byte level

Date: 2026-09-13
Status: Accepted
Story: S5.7.1 Test Generator: build and evaluate (E5, F5.7, WBS 2.5.13, 2.5.14)

## Context

This is the last agent of the Agents plane (E5). A config's own `dq_rules` already name every outcome a table's rows must not violate; a person turning each into a unit test and a sample file that actually trips it is mechanical but slow. Two things did not exist anywhere in this repository before this story: a way to render a spec's fields *backward* into a fixed-width line (every pattern so far only parses forward), and a "branch coverage" metric for rules at all (a real term in the product spec's own agent table, never implemented).

## Decision

1. **No model in the loop.** Every branch this agent knows how to synthesize is read straight off a `dq_rule`'s own typed fields — `kind`, `field`/`fields`, `values`, `min`/`max`, `trailer_field` — the same reason DQ Generator needs none. The one kind with no fixed shape, `condition` (a free SQL string), is handled by recognizing exactly the one pattern DQ Generator itself is known to produce (`FIELD <= CURRENT_DATE()`); any other condition is reported as not covered rather than a model guessing what arbitrary SQL means.

2. **A synthetic file is built forward, not corrupted from something real.** `render_record`/`render_synthetic_file` assemble a complete, minimal file — header, one detail line, trailer — from the spec's own field positions, entirely from a fixed, small, programmatic vocabulary (`default_value`: the field's first declared code, an all-zero digit string for an unsigned numeric picture, a fixed placeholder date, or `SYNTH`-padded text). Every branch changes exactly one field from this baseline to the value that trips its rule and nothing else — a duplicate key is two otherwise-identical lines, a future date overrides one date field, a control-total mismatch overrides only the trailer's count. "Contains no real records" (this story's own guardrail) is therefore architectural: this module has no code path that reads a real sample file, reference data, or anything outside the spec and config it was given — a test proves `render_synthetic_file` opens no file at all.

3. **An edge value is only rendered when it can actually exist as raw bytes.** `price_not_negative`'s `min: 0` is the real, committed example of why this matters: "one below the minimum" is `-1`, and an unsigned numeric picture (every field in this repository's real specs) cannot hold a negative raw digit string. The SQL assertion is still generated — the check is valid at the logical, converted level regardless — but no edge *file* is rendered for that branch, and the report says so rather than emitting a byte pattern that could never occur in a real file. A field with implied decimals would need its boundary value scaled into raw digits to render one correctly at all; this first version does not yet do that scaling, so a `range` rule on a decimal-scaled field only gets a file when its boundary happens to need no scaling — a known, narrow limitation, not a silent wrong answer.

4. **The SQL assertion mirrors `astra_knowledge.cdm.render_tests`'s own convention** — "a test returns failing rows" — with `{{ DATABASE }}.{{ SCHEMA }}.{{ TABLE }}` placeholders the same shape `{{ DATABASE }}` already is in rendered DDL, since this agent has no way to know the real Bronze/Silver table name the compiler (S3.2.x) will eventually render — guessing one and being wrong would be worse than a clearly-marked placeholder a person fills in. `control_total`'s own SQL needs two tables (the detail rows and the trailer's own count), so it gets two placeholders (`{{ DETAIL_TABLE }}`, `{{ TRAILER_TABLE }}`) rather than pretending one table name covers both.

5. **"Branch coverage of rules" is a completeness metric this agent computes directly, not a judgment a person had to review first.** Unlike Spec Reader's or Modeler's own accuracy metrics, there is no human-reviewed "correct" test suite to compare against — the correct answer is simply "every dq_rule this agent's generators support got at least one branch," which is checkable without a person in the loop. `TestDraft.coverage` is exactly that fraction, and `agents/test_generator/`'s gold set is real, not illustrative (the same shape Pattern Matcher's is): it scores coverage against the real, already-committed `configs/examples/pershing_position.yaml`, whose three `dq_rules` (`control_total`, `not_null`, `range`) are all kinds this agent fully supports — so the threshold is 1.0/1.0 on purpose; anything less on this specific config would be a real regression, not an expected shortfall.

6. **Rule catalog entries (prose rules, not `dq_rules`) are out of scope.** A rule's `text` has no structured outcome path to enumerate the way a `dq_rule`'s `kind`/`values`/`min`/`max` does; turning "an OP position's stored quantity is the file's quantity divided by 100" into a concrete branch needs the same kind of semantic judgment Rule Recovery's own `candidate_tests.yaml` was explicitly left unfinished for. Consuming `candidate_tests.yaml` and translating its free-text `given`/`expect` into synthetic data would need an LLM, breaking this agent's fully-deterministic design — left for a later story, not silently declined.

## Consequences

- `resolution` (account/security found/not-found/closed/ambiguous/inactive) is not covered by this agent: any synthetic file with a `SYNTH`-prefixed identifier already, trivially, is a "not found" case by construction, so a dedicated branch for it would not be a distinct edge case — resolution's real branches need reference-data awareness this agent does not have.
- The `{{ TABLE }}` (and `{{ DETAIL_TABLE }}`/`{{ TRAILER_TABLE }}`) placeholders are new — the first ones this repository has needed beyond `{{ DATABASE }}` — because no agent before this one generated SQL against a table it could not otherwise name. Wiring them to the compiler's real naming convention, once S3.2.x's own table names are available to read, replaces a placeholder with a real reference and changes nothing else about this agent's design.
- A `range` rule on a field with implied decimals only gets a fully correct edge file when its boundary needs no scaling into raw digits; scaling it correctly is a natural, bounded follow-up once a real client engagement needs it, not a redesign.
