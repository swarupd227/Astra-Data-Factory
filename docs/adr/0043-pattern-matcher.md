# ADR 0043: The Pattern Matcher compares detail-record shapes, not field names, and never invents a family

Date: 2026-09-13
Status: Accepted
Story: S5.3.1 Pattern Matcher: build and evaluate (E5, F5.3, WBS 2.5.5, 2.5.6)

## Context

A custodian's Source Spec needs a family (which other specs share its layout, for reuse), a tier (`simple`/`medium`/`complex`, the vocabulary a source config's own `tier` field already uses) and a pattern list, so that onboarding does not need a person to eyeball a new layout against every spec already in the registry. `astra_knowledge.registry.Registry.unclassified()` already exists for this — "specs with no family yet: the Pattern Matcher has not classified them" is its own docstring, written before this agent did.

## Decision

1. **Family similarity compares detail records only, by field shape, never by field name.** Two custodians name the same kind of field differently (`account_number` vs `acct_no`), so a name-based comparison would only ever match a custodian against itself. Each field is reduced to `(picture kind, declared type)` — `("alphanumeric", "string")`, `("numeric", "decimal")` and so on — and two detail records are compared with a longest-common-subsequence ratio over that reduced sequence, tolerant of a field inserted or dropped between versions. Header and trailer records are ignored entirely: they are almost always a generic record-type-and-control-total shell common to unrelated layouts, and including them would swamp the one part of a file that actually says what kind of file it is.

2. **A spec's own declared family always wins; similarity only runs for a spec the registry has no family for.** Re-running the agent on an already-classified spec reports its own family, tier and pattern list back — informational, not a re-guess. This mirrors `Registry.unclassified()`'s own framing: the job is to fill in what a person has not set yet, not to second-guess what they have.

3. **Two structural gates run before any similarity score is computed**, both hard, both zero the score outright: a different file format (`fixed_width` vs `delimited`), or a different `file_type` (`position` vs `transaction` vs `price`). A family groups files that are the same kind of thing; two files that are not even physically read the same way, or that carry a fundamentally different kind of data, are never candidates no matter how their fields happen to line up. A third, softer signal — the count of detail record types (one flat detail record vs. an A/B pair) — multiplies the similarity score by 0.3 rather than zeroing it, so a real near-miss is visible in the report even when it correctly falls below the reuse threshold.

4. **`FAMILY_THRESHOLD = 0.7` is calibrated against the two real data points this repository has**, not chosen arbitrarily: the same family's two real spec versions on file — `pershing_gcus` 2017-07-25 and 2026-01-01, one field (`lot_id`) added between them — score 0.94; the nearest *different* family in this repository (`split_position_example`, an A/B paired layout against `pershing_gcus`'s single flat detail record) scores 0.11 after the detail-count penalty. 0.7 sits with a wide margin on both sides of that gap, verified in `agents/pattern_matcher/gold/`, not asserted from theory.

5. **A spec below the threshold gets no family at all — `family: null`, `new_pattern_proposal: true` — not a guess and not an invented family name.** There is no ticketing or review-queue system anywhere in this repository (the Control plane workbench, E1, has not started) to route a proposal into; the "architect queue" the backlog asks for is implemented the same way every other agent's findings are here: a report a person reads, with the proposal called out in its own section, naming the nearest known family and its similarity score so a reviewer can tell at a glance whether the threshold missed a real match or this genuinely is something new. Deciding to name a new family, or to reuse an existing one despite the score, is exactly the kind of judgment call this agent is not trusted to make for itself — the same "agent proposes, human approves" shape Spec Reader's own draft-not-registry write already established.

6. **Tier is a small, explicit point score, not a black box.** No pilot data yet ties a specific structural signal to actual onboarding time (the KPI in product spec Section 14 is measured by tier, not derived from one), so seven round-number signals stand in for now — more than one detail record type, a merge rule, a pairing, a split rule, a lifecycle rule, more than 30 real fields, a record length or column count past 300/20 — one point each, `complex` at 3+, `medium` at 1+, `simple` at 0. This reproduces the one tier already on file in this repository (`configs/examples/pershing_position.yaml`'s `pershing_gcus` at `tier: medium`, which this rule also scores 1/medium) and is cheap to recalibrate once real onboarding-time data exists, because every signal and its weight is named in one place (`tier_score`), not folded into an opaque similarity number.

7. **The pattern list needs nothing new.** `astra_knowledge.patterns.patterns_for(spec)` already classifies a spec against the pattern library by file format; this agent calls it as-is. Building a second, agent-specific pattern classifier would risk it disagreeing with the one the generation plane and every other pattern-aware tool already use.

8. **The gold set is real, not illustrative — the first of its kind in this repository.** `agents/examples/spec_reader/eval.yaml` is explicitly a stand-in, because Spec Reader's real gold set needs a person to review a real extraction first. This agent's does not: "known custodians" means exactly the specs already committed to this repository's own registry, and correctly withholding a family from a genuine singleton is as much a correct answer as correctly reuniting a spec with its own sibling. `agents/pattern_matcher/gold/specs/` is a copy of the real `specs/` directory with every family hidden except `pershing_gcus/2026-01-01` (the sibling a correct run should find); `agents/pattern_matcher/eval.yaml` and `predictions.yaml` sit at `agents/pattern_matcher/` — one level under `agents/`, matching `astra_verification.agent_eval.discover`'s own glob — rather than under `agents/examples/`, so `astra-verify agent-eval check|report agents` (already run in CI and the weekly workflow) picks it up for real.

## Consequences

- The 0.7 threshold and the tier score's round numbers are both first-pass calibrations against a small, illustrative registry (five specs, four families). Real custodian onboarding will either confirm them or, more likely, need `agents/pattern_matcher/gold/` to grow with real reviewed cases before either number is trusted further than "directionally reasonable."
- A field-shape comparison has a known blind spot: two files that happen to share the same type sequence (code, string, string, decimal, code, ...) for unrelated reasons could score higher than their fields actually warrant. The detail-count and file-type/format gates catch the cases this repository's own specs demonstrate; a real false-positive, if one turns up, is evidence for a stronger signal (field length, not just kind), not for abandoning the approach.
- `merge`, `pairings`, `splits` and `lifecycle` feed the tier score but not the family similarity score; two specs that are the same underlying layout but one has, say, a lifecycle rule and the other does not, would still match on their field shapes. This is intentional — those rules describe how a file's *rows* behave over time, not what the file's fields are — but is worth revisiting if it ever produces a bad match in practice.
