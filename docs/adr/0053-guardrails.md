# ADR 0053: Guardrails is a closed level, an open task class, and a change that either clears the bar or is never written

Date: 2026-09-13
Status: Accepted
Story: S5.13.1 Guardrails and autonomy: build and evaluate (E5, F5.13, WBS 2.5.24)

## Context

The product spec names the whole vocabulary this story enforces, word for word (Section 8, "Human-in-the-loop and autonomy"): four levels — L0 Observe, L1 Suggest, L2 Prepare, L3 Act with audit — "every agent task class has an autonomy level," "level change requires approval and is logged" (this story's own AC1, restated), and "promotion to L3 requires a measured acceptance rate above a threshold over a stated window" (this story's own AC2, restated). Nothing here is invented; this agent's whole job is making that paragraph true in code rather than in a policy document nobody enforces.

One thing in this plane already had L3-shaped behavior before this story existed: Exception Triage (S5.8.1) auto-applies a suggestion when its rejection code is whitelisted (`auto_resolve: true`) and its own measured per-code confidence clears `AUTO_APPLY_CONFIDENCE = 0.8` — the taxonomy's own schema names this agent by name for exactly this ("Exception Triage may apply the resolution without a person (autonomy level L3, with audit)"). That gate is real and stays; it answers "has this specific rejection code, on its own track record, earned trust." It does not answer the separate question this story adds: "is Exception Triage's whitelisted-exception-classes task class, as a whole, currently authorized by an architect to act at L3 at all." A per-code confidence number is not an architect's approval, and nothing before this story recorded that approval, or logged when it changed.

## Decision

1. **Level is a closed, four-member enum; task class is an open string.** `Level.L0`..`Level.L3` are the only four values `astra_agents.guardrails.Level` can hold — the spec's own table, not a vocabulary an agent or a client extends. `task_class` is free text (`"rule_recovery"`, `"docs"`, `"whitelisted_exception_classes"`, ...) because the spec gives *examples* per level, not a closed list — new agents and new task classes will be named over time by whoever operates the factory, the same way `exception_triage.Decision.code` and `gate_evidence_compiler.Approval.release` are free strings for the same reason.

2. **The log is the state; there is no second "current level" file that could disagree with it.** `record_change` appends one `LevelChange` — agent, task_class, level, approver, reason, when, and (for L3) evidence — to an append-only YAML log and rewrites it, the exact shape `astra_agents.exception_triage`'s decisions log and `astra_agents.gate_evidence_compiler`'s approvals log already use. `current_level` is simply the most recent entry for that (agent, task_class) pair; an (agent, task_class) never mentioned is `Level.L0` by construction — "new agent or new domain pack in shadow mode" is the product spec's own words for that exact case, so a missing entry defaults to the safest level rather than raising `GuardrailsError`.

3. **Every change needs an approver and a reason, full stop — this is AC1, not a suggestion.** `record_change` raises `GuardrailsError` and writes nothing for a blank agent, task class, approver or reason, or an invalid level string. There is no "unapproved, pending" state this log can hold — a change either has an approver and a reason, or it is refused before it is ever written, so nothing in the log can later be read as "not yet approved."

4. **A change *to* L3 additionally needs evidence that clears a fixed bar — this is AC2 — checked before a single byte is written, never after.** `Evidence` carries `acceptance_rate`, `sample_size` and `window` (what the rate was measured over — "trailing 90 days", "last 40 decisions", whatever the architect actually measured). `L3_ACCEPTANCE_THRESHOLD = 0.8` is the same bar `exception_triage.AUTO_APPLY_CONFIDENCE` already holds a single code's own track record to — deliberately not imported from there and not code-coupled to it (a task class's promotion evidence and one rejection code's own rolling confidence are different measurements over different populations), but chosen to agree with it rather than invent a second, different number for the same idea the spec describes once. `L3_MINIMUM_SAMPLE = 20` has no derivation in the spec; it is this module's own floor, named so a rejected promotion's error says exactly what was short (the rate, the sample, or the window statement) rather than a bare "no". A change to L3 that fails either check raises `GuardrailsError` and writes nothing — the rejected attempt is never recorded and flagged for someone to notice later; it simply does not happen, matching how this session's other agents never write a fabricated value ("never invented, never a model's guess").

5. **Enforcement is a real call site, not only a data structure.** `permits(changes, agent, task_class, required)` is the query every agent's own code can consult before acting autonomously. Exception Triage is retrofitted, additively: `exception_triage.gate_auto_apply(draft, authorized=...)` forces every suggestion's `auto_apply` back to `False` when the task class is not currently authorized at L3, applied on top of the agent's own per-code confidence gate, never instead of it — a suggestion still needs both its own earned confidence *and* the task class's own architect-approved authorization to auto-apply. `astra-agents exception-triage run --guardrails <log>` is the new, optional flag; omitted, the command behaves exactly as it did before this story (every existing test of that command is untouched and still passes), so this is additive, not a breaking change to an already-shipped, already-tested agent.

6. **The Control plane's own real autonomy admin surface does not exist yet (S6.3.12, WBS 2.6.24) — this is a real, working stand-in, the same relationship the Gate Evidence Compiler's approval log already has to the Control plane's own approvals API (ADR 0051).** `astra-agents guardrails set-level`/`status` are that stand-in: a person (today, a CLI operator; later, S6.3.12's UI) records a change, and `status` reads the current level of every (agent, task class) the log has ever mentioned. Nothing here schedules the spec's own "reviewed monthly" cadence — that is a process an architect follows by recording a fresh change (with fresh evidence, for L3) each month, not something this CLI enforces by a clock; a later Control-plane story can add that.

## Consequences

- `astra_agents.guardrails` has no gold set: like the Gate Evidence Compiler and the Docs & Runbook Writer before it, its acceptance criteria are behavioral (a change needs approval and is logged; a change to L3 needs evidence above a threshold), proven directly by `test_the_story_acceptance_criteria_are_satisfied`, not a precision/recall number.
- Exception Triage is the only agent retrofitted in this story. Any other agent whose own task class an architect wants gated the same way (the spec's own L3 examples also name "drift config deltas in non-prod" and "cost sizing") gets the same treatment later, one small `gate_*` function plus one optional CLI flag at a time — this story does not attempt all of them at once.
- `guardrails set-level`/`status` exit codes do not follow the eleven draft agents' 0/1/2 convention (there is no draft state to flag with exit 1): 0 on success, 2 when a change is rejected. `cli.py`'s own module docstring documents this as deliberate, the same way it already documents `docs-writer`'s own different exit-code shape.
