# ADR 0046: The DQ Generator reads rule kinds straight off the spec's own structure, never a fabricated threshold

Date: 2026-09-13
Status: Accepted
Story: S5.6.1 DQ Generator: build and evaluate (E5, F5.6, WBS 2.5.11, 2.5.12)

## Context

Five categories of DQ rule are cheap for a person to write once they have read a layout closely enough — a trailer's control total, a sign field's declared codes, a date field's plausibility, a record's natural key, a pairing's completeness — and expensive to keep re-deriving by hand for every new custodian. All five turn out to be things `astra_knowledge.registry.SourceSpec` already parsed: a trailer field, `Field.sign_field` and `Field.codes`, `Field.type`, `spec.merge.keys` / `pairing.keys`, `spec.pairings`. Nothing about generating them needs a model.

## Decision

1. **No model in the loop.** Unlike Spec Reader, Rule Recovery and the Modeler, this agent reads structure a parser already extracted rather than judging meaning a document or legacy code only states in prose — the same reason Profiler and Pattern Matcher need none. `generate(spec, targets=...)` is pure, deterministic code; every rule kind is one function (`generate_control_total_rules`, `generate_sign_field_rules`, `generate_date_rules`, `generate_key_rules`, `generate_pairing_rules`) reading exactly the spec attributes named above.

2. **"Thresholds default to the client's targets, never invented" (product spec Section 6) is honored by needing no invented number in the first place**, not by inventing one and calling it a default. None of the five categories needs a fabricated threshold: a control total is exact (a count equals a count), an accepted-values check is the field's own declared codes, a date check is bounded by `CURRENT_DATE()` rather than a guessed cutoff, a key is exactly what `merge`/`pairing` already declares, and a pairing check is a plain not-null on a field only the second paired record contributes. What a client's own engagement DOES get to set is `severity` — how strict a violation is treated — through an optional `--targets` file (`severity: {control_total: ..., sign_field: ..., date: ..., key: ..., pairing: ...}`), one entry per category; a category not named there gets `"error"`, the same flat default `astra_data.dq` already falls back to when a config's own `dq_rules[].severity` is omitted (`generation/src/astra_data/dq.py`). No per-kind default was invented here beyond mirroring that one already-established fallback.

3. **A control total is only generated when it is unambiguous.** A trailer field is recognized by a naming convention every spec this repository has ever seen actually follows — the name ends in `count` (`detail_count`, `record_count`) — and only when the spec has exactly one detail record type. A spec with two detail record types sharing one trailer count (like `split_position_example`'s `holding`/`valuation`) has no way to say which type, or what combination, the one number covers, so nothing is generated rather than a rule that would be wrong for one of the two record types half the time. This is directly demonstrated: `pershing_gcus` (one detail type) generates a control total; `split_position_example` (two) generates none.

4. **A pairing check reuses `not_null`, not a new schema kind.** `config-v0.schema.json`'s `dq_rules[].kind` has no dedicated "pairing completeness" kind, but its `level: pair` already exists for exactly this: after pairing, a row with no match in the second record type has nulls where that record's fields would be. A `not_null` check at `level: pair` on the first real field the second paired record contributes (excluding the pairing's own keys, and `filler`) is a pairing-completeness check using only what the schema already has — the same reasoning ADR 0045 used for CONFIRM_WITH_LOADER: reuse a real, existing primitive rather than add a new one for a single story.

5. **Every generated rule is independently re-validated against the real `config-v0.schema.json`**, wrapped in a minimal stub of the config fields this agent does not draft (`source`, `spec` identity, `target_profile`, `domain_pack`, `owner`) so only the `dq_rules[]` portion of the schema is actually exercised — the same "propose, then re-check against the real schema" shape every other agent in this plane uses, even though this agent has no model output to distrust; a test proves a deliberately malformed rule is still caught.

6. **No eval gold set.** Unlike Spec Reader, Pattern Matcher and the Modeler, this story's acceptance criteria are behavioral ("control-total, sign-field, date, key and pairing rules generated for GCUS"), not a precision/recall percentage — the same shape Profiler's and Rule Recovery's own acceptance criteria took, and both skipped a formal `eval.yaml` for the same reason: a gold set with a statistical threshold measures something this story does not ask for. `test_the_story_acceptance_criteria_are_satisfied` in this story's own test suite proves the behavioral criteria directly, against the real `pershing_gcus` spec for the first four categories and the real `split_position_example` spec for pairing (since `pershing_gcus` itself has no pairing block to exercise that category against).

## Consequences

- `range` and `not_null`-outside-of-pairing (the two other kinds `config-v0.schema.json`'s `dq_rules` supports, and the two the real `configs/examples/pershing_position.yaml` already hand-writes for GCUS — `cusip_present`, `price_not_negative`) are out of this story's scope on purpose: both need a number or a field this agent has no structural way to derive without guessing, which is exactly the fabrication the guardrail forbids. A future story could add them once there is a real source for the number (a domain pack default, a client's own stated tolerance) rather than this agent inventing one.
- The trailer-count naming convention (`*count`) is a real heuristic, not a certainty; a custodian whose trailer names its count field something else (`RECCNT`, `NBR_RECS`) produces no control-total rule rather than a wrong guess — visible in the report as a category with zero rules, not a silent gap.
- `render_dq_rules_yaml` produces a `dq_rules:` block in the exact shape a real config's own section takes, so promoting a reviewed draft is pasting it in, the same "draft, then a person moves it" shape as every other agent's output here.
