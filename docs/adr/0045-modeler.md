# ADR 0045: The Modeler can only target a CDM column it was given, and never writes a CDM change itself

Date: 2026-09-13
Status: Accepted
Story: S5.5.1 Modeler: build and evaluate (E5, F5.5, WBS 2.5.9, 2.5.10)

## Context

The Modeler maps a Source Spec's fields to the domain pack's canonical model, proposes resolution parameters and a conservative set of DQ suggestions, and drafts the config the pipeline generator will eventually render from. Unlike Pattern Matcher and Profiler, mapping `cusip` to `position.custodian_security_id` needs the same kind of semantic judgment Spec Reader and Rule Recovery need — a raw layout field name and a canonical business column rarely look alike — so this is the third agent in this plane to call a real model.

## Decision

1. **A mapping's `target` is a closed enum built from the domain pack's own latest model, not a free string.** `cdm_targets(model)` reads every entity and column from `astra_knowledge.cdm.load_pack` (lineage columns excluded — the pipeline fills those, not a mapping) and the tool schema's `target` property is exactly that list. The model cannot propose `position.custodian_id` when the real column is `position.custodian_security_id`; the closest-sounding wrong answer is exactly as invalid as a nonsense one. `_translate_mapping` re-checks the target against the same list independently of the tool schema, the same "structural guardrail, verified again in code" shape Spec Reader and Rule Recovery already use.

2. **A transform is only ever what `astra_data.transforms.parse_transform` accepts.** This is the exact function the compiler itself calls; a proposed transform this agent could not parse is a mapping problem, not a silent pass — there is no second, agent-specific notion of what a valid transform call looks like.

3. **A breaking CDM change is a request, never a write.** `build_cdm_change_request` builds a real candidate `Model` (the current one with one proposed column added to one entity, via `dataclasses.replace` — `Model` and `Entity` are already frozen dataclasses, so this needs no new machinery) and calls `astra_knowledge.cdm.diff` against the current model — the exact function the domain pack's own version-to-version checks already use to decide breaking vs. additive. Nothing is ever written under `domains/<pack>/cdm/`; a test proves this directly, by hashing the real model file before and after building a draft with a breaking request and confirming it is untouched. `ConfigDraft.breaking_change_requests` is exposed for a person to read and, if they agree, is who actually bumps the model's version and writes the migration note — this agent stops at the request, per ADR 0013's own consequences ("the Modeler agent... raises CDM change requests as new model versions... before a steward sees it"). Rendering the full version-bumped YAML file for a steward to `git mv` into place is a natural next refinement, not built here: the request's content (entity, column, type, breaking classification, reason) is what a steward needs to decide, the same way Rule Recovery's candidate tests are a starting point rather than a runnable one.

4. **`CONFIRM_WITH_LOADER` did not exist anywhere in this repository before this story** (a repository-wide search turned up only the acceptance criterion itself). Rather than add a new field to `rule-v0` or `config-v0` for it, a rule the Modeler proposes that needs checking against the legacy Loader's real behavior — an ambiguous sign convention, a business rule the spec states but a real file might contradict — is written the exact way Rule Recovery already writes a new rule (`status: recovered`, never anything else, `astra_knowledge.rules.Rule`/`render_rule`), tagged `confirm_with_loader` in `tags` (the schema's own pattern is lower-case only; a report renders it CONFIRM_WITH_LOADER for a person to search for). `dedupe_name`, `rule_to_dict` and `validate_rule` are imported directly from `astra_agents.rule_recovery` rather than re-implemented — the same rule-v0 shape, the same independent re-validation, one definition of what a valid recovered rule looks like.

5. **DQ suggestions are a conservative subset of the real `dq_rules` shape, not a lesser one.** `config-v0.schema.json` already has a complete `dq_rules` array (six kinds, citations, severities, owners) that a separate, not-yet-built agent (DQ Generator, F5.6) will fully populate. The Modeler proposes only `not_null` and `unique` — the two kinds inferable straight from what a spec field already declares (`required`, a record's key) without any of DQ Generator's own judgment about thresholds or control totals — in the same canonical shape a `dq_rules` entry would eventually take, so a suggestion is a head start on a real one, not a translation problem later.

6. **`AnthropicClient` is duplicated a third time, not shared**, for the same reason `astra_agents.rule_recovery.AnthropicClient` is: the streaming-and-token-budget shape came from real debugging against a live account (ADR 0041's consequences), and refactoring it now, still with no live account in this session to re-prove it against, risks quietly reintroducing a bug that has already been found and fixed once.

7. **The mapping precision/recall gold set is illustrative, the same as Spec Reader's, for the same reason.** `configs/examples/pershing_position.yaml` is the only committed config in this repository with a matching spec, and it is a real, human-written, already-reviewed answer — but proving precision/recall against it needs a real model run this session cannot make (no `ANTHROPIC_API_KEY`). `agents/examples/modeler/eval.yaml` states the real config's seven mappings, its resolution block and its one `not_null`-shaped DQ rule as canonical items; `predictions.yaml` is deliberately short two items (the same "deliberately imperfect" teaching example Spec Reader's own gold set uses), so medium tier's recall visibly falls under its 90% threshold — the regression S4.3.4's harness exists to catch.

## Consequences

- Only `resolution.account` and `resolution.security` are modeled; `transaction_code` and `price` are real parts of `config-v0.schema.json` this agent does not yet propose, because the one real example does not exercise `transaction_code` and `price`'s own resolution (`when`/`lookback_days`) needs no field-level inference the way account/security identifiers do. Extending to them is adding cases to the tool schema and `_translate_mapping`'s counterpart, not a redesign.
- `agents` now depends on `astra-data` (the generation plane) for `config-v0.schema.json` and `astra_data.transforms` — the first cross-plane dependency an agent has taken, mirrored in `agents/pyproject.toml`, `.github/workflows/ci.yml`'s `agents` job, and `agents/pyproject.toml`'s `pythonpath`.
- No live call against a real Anthropic account has proven this agent yet, for the same reason Rule Recovery's had not (ADR 0044's own consequences repeat here): whoever runs the first real extraction should expect to be the first to see whether the prompt and tool schema hold up.
