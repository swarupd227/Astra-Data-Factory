# ADR 0044: Rule Recovery writes rule-v0 entries with a status the agent cannot change, and checks its own coverage

Date: 2026-09-13
Status: Accepted
Story: S5.4.1 Rule Recovery (Astra RE Harness): build and evaluate (E5, F5.4, WBS 2.5.7, 2.5.8)

## Context

A legacy Splitter/Loader's Java source encodes business rules — what gets rejected and why, what a value means, how it is transformed — that nobody has written down anywhere else. Rule Recovery reads that source and proposes rule catalog entries (`rules/<group>/<name>.yaml`, `astra_knowledge.rules`, ADR 0016) with a citation to exactly where each rule lives in the code, so a steward reviews a citation instead of re-reading the whole file. This is the third agent in this plane and the second (after Spec Reader) that genuinely needs a model in the loop: classifying what a block of legacy code *means* as a business rule, and drafting a test that would prove it, is code comprehension, not something a fixed-width parser or a similarity score can do.

Two things this repository does not yet have made two decisions unavoidable before any code could be written, both put to the user directly rather than assumed: whether to call a real model (as with Spec Reader) or stay deterministic, and what to run it against, since no real Splitter/Loader Java exists anywhere in this repository — `docs/backlog-v0.2.md`'s own Risks section says as much ("confirm what the Envestnet Splitter/Loader actually is"). The answers were a real Anthropic call, mirroring Spec Reader, and a hand-authored illustrative fixture, standing in for real source the same way the illustrative specs stand in for a real layout document.

## Decision

1. **The model never gets a `status` field to fill in.** `EXTRACTION_TOOL`'s schema has no `status` property at all — the tool call cannot express one, so there is nothing for a model to get wrong here. `build_draft` always writes `status: "recovered"` and a single `history` entry `by: "rule-recovery"`, regardless of anything else in the raw extraction (proven directly: feeding `_translate_entry` a raw dict with a smuggled `"status": "confirmed"` key still produces a recovered entry, because the field is never read). Confirming or rejecting a recovered entry is `astra-spec rules set-status`'s job — the same command a steward or the workbench will call, per ADR 0016's own consequences — never this agent's.

2. **Every rejection code the source actually defines is checked against, not just claimed.** `find_rejection_codes` scans the raw Java text independently of the model, with its own regex (`"L###"`, calibrated to this story's illustrative fixture's own convention — the real Loader's convention is unknown, so this is the first thing to recalibrate once real source arrives). `RecoveryDraft.rejection_codes_untraced` is the set difference between what the scan found and what the recovered entries' own `rejection_codes` cover; a real run reports this gap in its own report section rather than letting "traced" mean whatever the model happened to remember. The committed example's four codes (`L001`-`L004`, one in the Splitter, three in the Loader) are all traced by a complete extraction, and a test proves the gap shows up correctly when one entry is missing.

3. **T-SQL is a second deterministic backstop, not just a prompt instruction.** `TSQL_MARKERS` looks for idioms specific enough to SQL Server that finding one is a reliable signal on its own — `GETDATE()`, `TOP n`, bracketed two-part identifiers, `sp_` procedures, `IDENTITY(`, `NVARCHAR` — independent of the illustrative fixture, so this part of the backstop should generalize to real code. `RecoveryDraft.tsql_lines_unrouted` is every such line the model's own `embedded_sql` citations do not cover. The guardrail this story asks for — T-SQL is routed to SnowConvert AI (ADR 0028's own migration path for the Loader's SQL Server database), not parsed — means the agent never turns a SQL snippet into a rule's `text`; the system prompt says so, and this scan catches a case where the model quietly missed one instead of routing it.

4. **A recovered entry is written as a real `rules/<group>/<name>.yaml` file, using the catalog's own code**, not a second serializer: `astra_knowledge.rules.Rule` and `render_rule` are called directly, and every draft file is independently re-validated against `rule-v0.schema.json` before being reported valid — the same "the tool schema is a guardrail, the registry schema is the safety net" shape Spec Reader established for `source-spec-v0`. `--group` (a CLI flag, not a model guess) decides the catalog group a run's entries belong to, since grouping is a placement decision a person should make, the same way Spec Reader's `--custodian`/`--file-type` are given, not inferred. `--owner-name`/`--owner-email` are required for the same reason `rule.owner` is required by the schema: recovered is not ownerless, it is unconfirmed by a named owner.

5. **Candidate tests have no home in `rule-v0` and no existing schema anywhere in this repository** (the Test Generator, F5.7, is a separate, unbuilt story). Rather than invent a rule-catalog field that does not belong there, or block this story on a schema that belongs to a different agent, each entry's candidate tests are written to a plain `candidate_tests.yaml` next to the draft — `{rule, description, given, expect}` — a starting point for a person (or, later, the Test Generator) to turn into a real test, explicitly provisional.

6. **`AnthropicClient` is duplicated from Spec Reader's, not shared.** Both need the same shape — stream rather than create (a real ~90-field spec already crossed the SDK's non-streaming timeout; the same risk applies here for a large Loader), a high token budget, a clear diagnosis when `stop_reason` is `max_tokens` — but that shape was arrived at through real debugging against a live account across three separate bugs (ADR 0041's own consequences). Refactoring it into one shared client now, with no second live account to immediately re-prove it against, risks quietly reintroducing one of those bugs for a savings of well under a hundred lines. The day a third agent needs the same client, sharing it becomes the better trade.

7. **The gold set is illustrative, not real — unlike Pattern Matcher's.** `agents/examples/rule_recovery/java/{Splitter,Loader}.java` are hand-authored, clearly labeled as such in their own Javadoc, and this is stated plainly rather than glossed over: there is no real Splitter/Loader source in this repository to build a real gold set from the way Pattern Matcher's leave-one-out fixture uses the real `specs/` registry. `agents/tests/test_rule_recovery.py`'s own `GOOD_EXTRACTION` (a hand-built, complete, correct extraction of the fixture) is what proves the story's three acceptance criteria end to end for now; a real gold set is a later story once real source exists.

## Consequences

- `REJECTION_CODE_PATTERN` (`"L###"`) is a placeholder tied to the illustrative fixture's own convention. It will very likely need to change — to a different literal pattern, a named-constant heuristic, or something else entirely — the day real Loader source is available, exactly as ADR 0041 flagged for its own first live run.
- No live call against a real Anthropic account has proven this agent yet, for the same reason Spec Reader's first version had not: this session has no `ANTHROPIC_API_KEY` in its own environment. Whoever runs the first real extraction — against the illustrative fixture, or against real source once it exists — should expect to be the first to see whether the prompt and tool schema hold up, the same expectation ADR 0041 recorded and the same three-bug process that followed it.
- `class` (ingestion/business/normalisation) is the only classification this story asks for; the richer taxonomy a steward might eventually want (which entity a rule concerns, its risk if wrong) is `tags`/`applies_to`, already in the schema and already available to a future refinement, not new work here.
